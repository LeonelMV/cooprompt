# Codebase map

Where each responsibility lives, how control and data flow through the code, and where to start for common changes. Terms are defined in the [Glossary](glossary.md); the reasons behind the structure are in [Decisions](decisions.md).

## `apps/server`

| File | Owns |
| --- | --- |
| [`src/cli.ts`](../apps/server/src/cli.ts) | Standalone entry point: reads the environment, resolves the data directory, generates or loads the access code, picks the build to offer (`COOPROMPT_INSTALLER_ZIP` and `COOPROMPT_INSTALLER_VERSION`, or the newest in `apps/desktop/release`), starts the server, prints its addresses, shuts down on signals. |
| [`src/server.ts`](../apps/server/src/server.ts) | `createCooPromptServer()`, also used by the desktop host: opens the database, fails turns left running, wires Fastify, the error handler, all routes and `/ws`; returns the addresses, the store, `setAccessCode()` and `setAuth()` (sign-in options applied without restarting), `announceRestart()` and `close()`. |
| [`src/routes.ts`](../apps/server/src/routes.ts) | JSON API: health, sign-up/sign-in/Google (with account linking), profile, devices, user search, chats, transcript items, turns, sending messages, cancelling, invitations; input validation and access checks. |
| [`src/hub.ts`](../apps/server/src/hub.ts) | WebSocket hub: `hello` authentication, devices, chat subscriptions, presence and typing, validation of executor messages, streaming drafts, per-chat turn scheduling (the queue, multitask turns up to `maxParallelTurns`, which devices may run them), cancellation, decision forwarding, fan-out (team-only messages' content only to connections that announced `team-messages`, `sendToMembers` for what members get with the chat closed), heartbeats; hooks for the automation scheduler (`onDeviceReady`, `onTurn`) and `stopTurn` with a reason. |
| [`src/team.ts`](../apps/server/src/team.ts), [`src/team-routes.ts`](../apps/server/src/team-routes.ts) | Team-only messages: the stand-ins (`teamStandIns`) that apps without `team-messages` and item requests without `include=team` get instead of their content; sending one (a `team` item, never a turn, with `team.message` to the other members) and sharing one with the agents (its author only). |
| [`src/files.ts`](../apps/server/src/files.ts) | Shared workspace API: change feed, uploads with optimistic concurrency, deletions, blob downloads; blob storage on disk. |
| [`src/attachments.ts`](../apps/server/src/attachments.ts) | Attachments: members-only upload (streamed, size-limited, typed from its bytes) and download (never as an active document), content-addressed storage, the files a message carries, the server's description of what executor items attach (`withServerAttachments`), deletion with the chat and of orphan uploads. |
| [`src/automations.ts`](../apps/server/src/automations.ts) | `Automations`: storage of automations and their runs, the scheduler (due runs, missed runs and catch-ups, no overlap, time limits), starting a run as a turn of its owner on their chosen computer, following its turn, and telling the owner and the chat's members. |
| [`src/automation-routes.ts`](../apps/server/src/automation-routes.ts) | Automation endpoints: validation (chat membership, connected device, schedule, permission mode, time limit) and the owner-only rule. |
| [`src/installer.ts`](../apps/server/src/installer.ts) | `/install` and `/instalar` scripts (English and Spanish), the `CooPrompt.zip` download, finding the newest build in a release folder (`latestRelease`), and the `app` announcement with its hash (`releaseDescriber`). |
| [`src/store.ts`](../apps/server/src/store.ts) | Data access over SQLite: users, sessions, chats, members, invitations, items (`seq`/`rev`), turns, workspace files; mapping rows to protocol types. |
| [`src/db.ts`](../apps/server/src/db.ts) | Schema, startup migrations, statement cache and transactions on `node:sqlite`. |
| [`src/auth.ts`](../apps/server/src/auth.ts) | scrypt password hashes, session tokens and their hashes, Google code exchange, ID token verification, allowed domains (`parseAllowedDomains`) and whether Google vouches for the email (`ownsEmail`). |
| [`src/errors.ts`](../apps/server/src/errors.ts) | `HttpError`, turned into JSON error responses. |
| [`test/helpers.ts`](../apps/server/test/helpers.ts) | Test harness: in-process server on a random port (`startServer({ accessCode, google, passwordAuth, maxParallelTurns, automations, dataDir })`, where `automations` sets the scheduler's clock and tick), `api()`, `register()`, `TestSocket` (with `closed`, and the `features` it announces). Also used by desktop tests. |
| [`test/fake-google.ts`](../apps/server/test/fake-google.ts) | `FakeGoogle`: a stand-in for Google's OAuth endpoints (authorization with PKCE, token endpoint, signing keys) for the server and desktop sign-in tests. |

## Main flows

**Startup and sign-in.** [`index.ts`](../apps/desktop/src/main/index.ts) creates `AppCore` → `init()` loads secrets and the shell environment, auto-starts the embedded server if configured, and connects the WebSocket when a session exists → [`Login.tsx`](../apps/desktop/src/renderer/src/components/Login.tsx) calls `auth.*` → [`routes.ts`](../apps/server/src/routes.ts) `/api/auth/*` returns a token → `Realtime` sends `hello` → [`hub.ts`](../apps/server/src/hub.ts) answers `ready`.

**Google sign-in.** `Login.tsx` calls `auth.google` in [`core.ts`](../apps/desktop/src/main/core.ts) (and `auth.cancelGoogle` to stop waiting) → `googleSignIn()` in [`google.ts`](../apps/desktop/src/main/google.ts) starts `startLoopback()` from [`loopback.ts`](../apps/desktop/src/main/loopback.ts) with the `state`, opens the browser and waits for the code → `POST /api/auth/google` → `exchangeGoogleCode()` in [`auth.ts`](../apps/server/src/auth.ts) exchanges it and verifies the ID token → [`routes.ts`](../apps/server/src/routes.ts) finds, links or creates the account (revoking the sessions of an account it takes over) and returns a token.

**A message becomes a turn.** [`Composer.tsx`](../apps/desktop/src/renderer/src/components/Composer.tsx) → `chats.send` in [`core.ts`](../apps/desktop/src/main/core.ts) → `POST /api/chats/:id/messages` → `Store.createTurn` → `Hub.scheduleChat` → `turn.run` to the executor's socket → `AppCore.onServerMessage` → `Runner.run` → [`engines/claude.ts`](../apps/desktop/src/main/engines/claude.ts), [`codex.ts`](../apps/desktop/src/main/engines/codex.ts) or [`cursor.ts`](../apps/desktop/src/main/engines/cursor.ts) → `EngineSink` → the publisher ([`publisher.ts`](../apps/desktop/src/main/runner/publisher.ts)) sends `turn.items`/`turn.delta` → the hub stores and fans out `items`/`turn.delta` → [`store.ts`](../apps/desktop/src/renderer/src/lib/store.ts) (renderer) → [`Transcript.tsx`](../apps/desktop/src/renderer/src/components/Transcript.tsx). `turn.finish` ends it and the hub starts what can run next. A multitask message (`parallel`) can start while other turns run; on the executor, `Runner.planSession` gives it a side session when the chat's main one is busy.

**An automation run.** [`AutomationEditor.tsx`](../apps/desktop/src/renderer/src/components/automations/AutomationEditor.tsx) → `automations.save` in [`main/automations.ts`](../apps/desktop/src/main/automations.ts) → `POST /api/automations` in [`automation-routes.ts`](../apps/server/src/automation-routes.ts) → `Automations.tick` in [`automations.ts`](../apps/server/src/automations.ts) finds it due → `begin` (or a missed run, and `catchUp` when the computer says `hello` again) → the owner's prompt, the label line and a turn with `automation` → `Hub.scheduleChat` → `turn.run` to the owner's computer → `Runner.execute` adds the unattended note and declines approvals and questions → `Hub.onTurn` → `syncRun` records the run and sends `automation.run` → `AutomationNotices` notifies and [`AutomationsView.tsx`](../apps/desktop/src/renderer/src/components/automations/AutomationsView.tsx) shows it in the inbox.

**A permission decision.** The engine asks (`canUseTool` in the Claude adapter) → `Runner.requestPermission` publishes a `permission` item and waits → the card in `Transcript.tsx` calls `decisions.respond` → on the executor it resolves locally; elsewhere it goes as a `decision` message → the hub checks who may decide and forwards it → `Runner.respond` resolves the request.

**Interrupt and send.** `Composer.tsx` sends with `interrupt` and the chosen `interruptTurnId` → `chats.send` → `POST /api/chats/:id/messages` creates a higher-priority turn that `interrupts` it and calls `Hub.cancelTurn(…, 'interrupt')` → `turn.cancel` reaches the executor → `Runner.cancel` stops the engine → `turn.finish` (cancelled) → the hub records "Interrupted by …" and starts the priority turn.

**Command palette.** Typing `/` (or `$` for Codex) in `Composer.tsx` calls `commands.list` → `claudeCommands()` (from `probeClaude()` in [`engines/claude.ts`](../apps/desktop/src/main/engines/claude.ts)), `codexCommands()` or `cursorCommands()` in [`commands.ts`](../apps/desktop/src/main/commands.ts) → filtered with `matchCommands()` from [`src/shared/commands.ts`](../apps/desktop/src/shared/commands.ts). At run time, `Runner.execute` handles `/new` and turns Codex commands into prompts with `codexPrompt()`.

**An attachment.** `useAttachmentDraft` in [`ComposerAttachments.tsx`](../apps/desktop/src/renderer/src/components/ComposerAttachments.tsx) calls `attachments.stage` → `AttachmentStore.stage` in [`attachments.ts`](../apps/desktop/src/main/attachments.ts) → `chats.send` uploads with `uploadStaged` (`POST /api/chats/:id/attachments` in [`attachments.ts`](../apps/server/src/attachments.ts)) and sends their ids with the message (`forMessage`) → the prompt item carries `attachments` → `Runner.execute` copies them with `materialize`, lists them with `attachmentNote` and passes them to the engine → [`AttachmentList`](../apps/desktop/src/renderer/src/components/Attachments.tsx) shows them through `cooprompt-media:` (`AttachmentStore.serve`, registered in [`index.ts`](../apps/desktop/src/main/index.ts)). Engines share media with `EngineSink.attach` → the publisher's `share` (`AttachmentStore.sharer`) → the item's `attachments`, checked by `withServerAttachments` in the hub.

**A team-only message.** `Composer.tsx` with **Team only** on (`composerMode`) → `chats.sendTeam` in [`core.ts`](../apps/desktop/src/main/core.ts) → `sendTeamMessage` in [`main/team.ts`](../apps/desktop/src/main/team.ts) (uploading attachments first) → `POST /api/chats/:id/team-messages` in [`team-routes.ts`](../apps/server/src/team-routes.ts): a `team` item, no turn → `Hub.publishItems` (the content to connections that announced `team-messages`, `teamStandIns` to the rest) and `team.message` to the other members' apps → `AppCore.teamNotice` notifies in the background and the renderer store marks the chat (`teamUnread`) → `TeamMessage` in [`Transcript.tsx`](../apps/desktop/src/renderer/src/components/Transcript.tsx), loaded with `include=team` by `chats.open`. The runner's catch-up asks without it, so it only sees stand-ins, which `renderCatchUp` leaves out. **Share with the AI** → `chats.shareTeam` → `POST /api/chats/:id/team-messages/:itemId/share` turns it into a `user` item without a turn.

**Workspace sync.** Opening a shared chat (`chats.open`) → `SyncManager.activate` → `WorkspaceSync.start` (pull, scan, watch) → uploads and downloads through [`files.ts`](../apps/server/src/files.ts) → `Hub.notifyFiles` sends `fs.change` → `WorkspaceSync.onRemoteChange` pulls.

**Hosting.** [`ServerSection.tsx`](../apps/desktop/src/renderer/src/components/settings/ServerSection.tsx) (or `ServerChoice` in [`Login.tsx`](../apps/desktop/src/renderer/src/components/Login.tsx) before signing in) → `host.start` → [`host.ts`](../apps/desktop/src/main/host.ts) → `createCooPromptServer` in [`server.ts`](../apps/server/src/server.ts). **Open tunnel** → `host.tunnel` → `QuickTunnel.open` in [`tunnel.ts`](../apps/desktop/src/main/tunnel.ts), which takes over or starts `cloudflared` and keeps checking it; its state reaches `tunnelChanged` in `host.ts`, which raises the address notice ([`TunnelNotice.tsx`](../apps/desktop/src/renderer/src/components/TunnelNotice.tsx)) until `host.dismissTunnelNotice`.

**An update.** `releaseDescriber()` in [`installer.ts`](../apps/server/src/installer.ts) puts `app` in `GET /api/health` → `Updater.check()` in [`updater.ts`](../apps/desktop/src/main/updater.ts) → [`UpdateBanner.tsx`](../apps/desktop/src/renderer/src/components/UpdateBanner.tsx) calls `update.download` → `Updater.download()` downloads and runs `verifyBundle()` → `update.install` → `installUpdate()` in [`core.ts`](../apps/desktop/src/main/core.ts) waits for running turns, then `Updater.install()` starts [`update-helper.sh`](../apps/desktop/resources/update-helper.sh) and the app quits (a host announces `server.restarting`) → the new version calls `confirmLaunch()` in [`index.ts`](../apps/desktop/src/main/index.ts) → the helper keeps it or rolls back.

## Start here for common changes

**A protocol message or field.** Edit the types in [`packages/protocol/src/index.ts`](../packages/protocol/src/index.ts). Client-to-server messages are handled in `Hub.onMessage` ([`hub.ts`](../apps/server/src/hub.ts)); server-to-client messages are applied in `AppCore.onServerMessage` ([`core.ts`](../apps/desktop/src/main/core.ts)) and in `handleServer` in [`lib/store.ts`](../apps/desktop/src/renderer/src/lib/store.ts). Older apps ignore unknown server message types; older servers reject unknown client message types, so prefer optional fields. Cover it in [`collaboration.test.ts`](../apps/server/test/collaboration.test.ts). See [`packages/protocol/AGENTS.md`](../packages/protocol/AGENTS.md).

**A server route.** Add it to [`routes.ts`](../apps/server/src/routes.ts) (or [`files.ts`](../apps/server/src/files.ts) for workspace files) using `currentUser`, `viewableChat`/`memberChat`, the `text()` validator and `HttpError`. Data access goes in [`store.ts`](../apps/server/src/store.ts); schema changes in [`db.ts`](../apps/server/src/db.ts) must be additive. Payload types belong in the protocol. New English error messages need a template in `ES_MESSAGES`. Test through `api()` in [`test/helpers.ts`](../apps/server/test/helpers.ts).

**An IPC method (renderer to main).** Declare it in `CooPromptApi` in [`src/shared/types.ts`](../apps/desktop/src/shared/types.ts), implement it in `buildHandlers()` in [`core.ts`](../apps/desktop/src/main/core.ts), and call it from the renderer with `call()`. The preload doesn't change. For pushes from main to the UI, add a `MainEvent` variant and handle it in the renderer store.

**A setting.** Add the field and its default to `SettingsData` in [`settings.ts`](../apps/desktop/src/main/settings.ts) (stored values are merged over the defaults; only `host` is merged one level deeper). Expose it through `SettingsView` and `settings.get`/`settings.update` in [`core.ts`](../apps/desktop/src/main/core.ts), and add UI in a section under [`components/settings/`](../apps/desktop/src/renderer/src/components/settings). Secrets go to the secret store instead.

**A UI string.** Write it in English with `t()` (renderer) or `tr()` (main) and add the Spanish entry to `ES` in [`i18n-es.ts`](../apps/desktop/src/shared/i18n-es.ts). Messages generated by the server, engines or runner need an `ES_MESSAGES` template. Rules: [Internationalization](development.md#internationalization).

**An engine capability.** Extend the adapter contract in [`engines/types.ts`](../apps/desktop/src/main/engines/types.ts), map it in [`claude.ts`](../apps/desktop/src/main/engines/claude.ts), [`codex.ts`](../apps/desktop/src/main/engines/codex.ts) and [`cursor.ts`](../apps/desktop/src/main/engines/cursor.ts), and pass it from [`runner.ts`](../apps/desktop/src/main/runner/runner.ts). A control that an engine can't honor is hidden for it, like the permission modes in [`shared/engines.ts`](../apps/desktop/src/shared/engines.ts). A new transcript item kind also needs `ItemKind` in the protocol, `EXECUTOR_ITEM_KINDS` in [`hub.ts`](../apps/server/src/hub.ts) and rendering in [`Transcript.tsx`](../apps/desktop/src/renderer/src/components/Transcript.tsx). A new model provider is a preset plus its environment in [`providers.ts`](../apps/desktop/src/main/engines/providers.ts).

**A slash command of CooPrompt's own.** List it in [`commands.ts`](../apps/desktop/src/main/commands.ts) (`NEW_SESSION` and `CODEX_TEMPLATES` are the existing examples) and handle it in `Runner.execute` ([`runner.ts`](../apps/desktop/src/main/runner/runner.ts)) before the engine runs, or turn it into a prompt in `codexPrompt()`. Descriptions are UI strings and need Spanish entries. Cover it in [`commands.test.ts`](../apps/desktop/test/commands.test.ts).

**How a tool call looks.** Kinds, key arguments and service detection live in `describeTool()` and `SERVICES` in [`lib/tools.ts`](../apps/desktop/src/renderer/src/lib/tools.ts); logos in [`lib/brand-icons.ts`](../apps/desktop/src/renderer/src/lib/brand-icons.ts) (Simple Icons paths); verbs, summaries and details in [`ToolActivity.tsx`](../apps/desktop/src/renderer/src/components/ToolActivity.tsx), with Spanish entries for new phrases. Cover it in [`tools.test.ts`](../apps/desktop/test/tools.test.ts).

**A connector source.** Add a reader to [`connector-sources.ts`](../apps/desktop/src/main/connector-sources.ts) that builds `ExternalServer`s with `toServer()` (setting `nativeFor`/`nativeName` if an engine loads it on its own), include it in `externalServers()`, add its id to `DetectedSource` in [`src/shared/types.ts`](../apps/desktop/src/shared/types.ts) and its label to `SOURCE_NAME`/`SOURCE_ORDER` in [`ConnectorsSection.tsx`](../apps/desktop/src/renderer/src/components/settings/ConnectorsSection.tsx), and test it against a fake home folder in [`connector-sources.test.ts`](../apps/desktop/test/connector-sources.test.ts). A catalog entry is one line in [`connector-directory.ts`](../apps/desktop/src/shared/connector-directory.ts).
